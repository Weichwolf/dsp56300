Processing states and guest peripheral RESET

WAIT and STOP retire once, preserve the CPU registers/CCR and leave PC at the
following instruction. run returns immediately with RunResult.state set to
waiting or stopped, possibly before consuming its requested instruction budget.
Further positive or zero budgets return zero retirement without fetching any
successor, changing Progress or issuing I/O. Core::processing_state reports the
same state. The core does not spin, sleep an OS thread or advance a board clock.
The embedder schedules the next event and treats waiting/stopped differently.

Wake contract

A waiting CPU accepts Core::interrupt only at the existing admissible boundary
and priority mask. Invalid vectors, masked levels and reentry leave it waiting.
Successful admission changes the state to running before vector execution.
If a subsequent vector fetch/EA/stack/I/O fails, the accepted wake is retained
and the ordinary explicit fail-stop fault applies; no service state is invented.
All ordinary vector/base-cost/frame and post-RTI/fast exclusion contracts remain.

A stopped CPU rejects direct interrupt admission. The host first detects IRQA,
models the relevant oscillator/PLL/delay behavior and completes that phase with
Core::resume_from_stop. This method changes only stopped to running, without
retiring an instruction, changing registers or inventing elapsed cycles. The
host then admits its highest pending enabled interrupt, or calls run when none
is pending. IRQA wake may therefore resume foreground execution even when IRQs
are masked. Calling resume_from_stop in WAIT/running/faulted execution, or from
a callback, is rejected. It is an IRQA completion contract, not a generic forced
resume, physical pin simulator or automatic priority arbiter.

Code-cache clearing and visible-register initialization do not wake either
sleeping state. Host memory accesses remain available. The architectural DSP
cache and any cached instruction words survive sleep/wake, including stale
contents after noncoherent backing-RAM edits. run(0) does not consume an event
or post-vector exclusion. Core::reset cancels sleep as part of the existing
library initialization operation; it does not invoke the guest RESET callback.
A register view alone is not a processing/cache/REP/vector checkpoint.
The functional debug interface can also leave WAIT/STOP through a host DE/JTAG
request, either halting in Debug mode or queuing an IME-selected interrupt. It
is distinct from normal IRQ/IRQA completion; see doc/debugging.txt.

Guest RESET

The RESET instruction is different from Core::reset or a physical RESET pin.
It calls Io::reset_peripherals(instruction_pc) synchronously. The derivative
must reset its peripherals and interrupt-priority state before returning true.
The core then retires RESET and continues with the next instruction, preserving
CPU registers, modes, stack/loop state and architectural cache. Cache preservation
follows the manual's unchanged-processor-state convention; complete derivative
reset side effects and hardware confirmation remain qualification work.

No Io, the default unimplemented callback, or false acceptance produces the
appended FaultKind::host_event. Its program-space address/value/pc identify the
requesting instruction, not an invented peripheral register. The failed RESET
does not retire, enter a sleep state or replace CPU registers with reset values.
The ordinary attempted-instruction PC advance remains visible; accepted earlier
external actions are not rolled back and later run calls cannot replay them.
Fault and processing state are separate: a host-event fault can report running
while execution remains stopped by the fault until library reset.

The callback sees canonical architectural registers, advanced foreground PC and
pre-retirement Progress. Its pc argument identifies the actual instruction,
including a repeated body or injected vector word. Fast vector RESET preserves
the foreground register PC and follows the ordinary vector callback contract.
read/register/progress/state inspection, supplied-memory mutation and code-cache
clearing are permitted. run/reset/set_registers/interrupt/resume_from_stop reentry
is rejected. Callback code is noexcept and must handle its own errors.

Single-word RESET can repeat: every iteration requires its own acknowledgement,
including encoded-zero REP=65536. Accepted iterations and their base costs remain
visible if a later iteration fails; LC and all prior host effects are retained.
RESET can run in the currently qualified fast-vector subset, in either slot;
WAIT/STOP are forbidden there and as REP bodies. Valid finite-DO tests place
RESET away from the prohibited loop-ending instruction positions.

Native execution and storage

WAIT/STOP end translated blocks. A successful helper that enters sleep stops
native continuation, and every backend checks processing state before further
dispatch. Tests require actual native arithmetic around RESET and IRQ/RTI wake,
including warm old-mode code, fresh Carry/scaling/RM and callback successor edits.
No new allocation is introduced for the processing state itself. On Clang 19
x64 it uses byte 331 of existing Cpu padding; RunResult.state uses prior padding
at byte 4. Cpu remains 384 bytes, Core::Impl 131648 and RunResult 40, with every
previous recorded field offset unchanged. This is layout evidence, not binary
compatibility of the extended Io vtable or a performance/cache-miss measurement.
Consumers rebuild against the updated header.

Qualification limits

Reference: DSP56300 Family Manual Rev.5 sections 2.3.3-2.3.5, 13-162,
13-170/171, 13-183 and appendix A,
https://www.nxp.com/docs/en/reference-manual/DSP56300FM.pdf
The current nominal base costs are RESET=7 and WAIT/STOP=10. Progress does not
include sleep time or calibrated PLL/oscillator/restart/bus/pipeline delays.
Physical RESET defaults/held-pin/boot processing, DE/JTAG/debug transitions,
DMA wake details, exact pending-event/pipeline arbitration, clock stabilization,
all numeric-mode interactions and complete legal sequence coverage remain open.
In particular, Core::reset is still library initialization, not a qualification
of the manual's complete physical-reset register defaults (including CP/IPL).
No peripheral/board emulation or successful hardware-isolated backend is added.
All three ISA rows remain partial; complete support/testing is still mandatory.
