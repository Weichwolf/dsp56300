Software exceptions and vector execution

The explicit ILLEGAL, TRAP and TRAPcc instructions use an internal pending
vector controller. It is CPU behavior, not derivative peripheral emulation.
The controller resides in Core::Impl and uses no new allocation per request;
the hot Cpu layout and the generated-code ABI remain unchanged. The consumer
continues using the same headers, caller-owned RAM, run and I/O interfaces.
Registers alone are still not a complete REP/IRQ/exception checkpoint.

A request retires without changing CCR. If its run budget ends there, no vector
or successor instruction executes. A later positive budget fetches the vector.
Every successfully executed vector instruction counts once, including a
single two-word fast instruction. One-word vector pairs can stop between words.
A long JSR saves the resume PC and SR, clears the qualified service-mode fields,
sets IPL to at most three, then leaves execution at the handler. RTI restores
the frame. A completed fast service resumes foreground execution without RTI.
The register PC remains the selected foreground resume address during fast
vector execution; the I/O callback pc argument identifies the vector access.
Callback and host program edits use the normal P invalidation contract.

Atomic entry and Core-owned begin_fetch capture both vector words before the
first slot executes (FM2.3.2.7/table2-7). A native first-slot P store cannot change
the accepted second opcode. The pair survives per-instruction retirement and
trusted checkpoints; the second slot performs no new program read. Its
instruction_fetch metadata retains exception_vector and the accepted opcode.
Peripheral acknowledgement belongs to the consumer: a completed second read
can precede completion of the remaining vector instruction. Do not infer the
end of native vector execution from peripheral acknowledgement or register PC.

Architectural Progress includes request and injected instruction retirement and
listed base costs. Internal vectors executed by run count as general helpers
in JIT statistics; direct host interrupt admission contributes to Progress but
not generated-code counters. Extra exception/pipeline/wait latency is not a
calibrated clock. Zero budgets never consume pending work or exclusion state.

The pending controller survives clear_code_cache. reset clears it; set_registers
is initialization of visible registers and does not restore hidden continuation.
Host interrupt admission cannot replace an active/pending internal request.
Level-three admission is supported even at IPL3, subject to the existing library
boundary policy; a long service saturates the mask at three. This is not a
complete nonmaskable-source arbiter or hardware pipeline model.

The implemented vector subset comprises unconditional short/effective JSR,
parallel ALU/data moves, NOP, MOVEM and MOVEP register/memory/program forms.
Fast MOVEM and register MOVEP cannot read SSH or load LA/LC/SP/SC/SSH/SSL,
following FM A.3.7. MOVEP direction is peripheral-relative, opposite to MOVEM;
the native register/operand implementation handles the accepted transfer.
One two-word fast instruction is admitted at the first vector word. Existing
long-call entry can use either vector slot.
Conditional/bit-call vector forms and other legal fast instruction classes are
still explicit unsupported cases. Decoder, EA, stack and I/O failures do not
retire the failed instruction; already accepted vector or address effects are
retained and later run calls do not replay them. Selected failure-state checks
are library contracts, not hardware bus-error/stack-exception rollback.

REP ILLEGAL coalesces one pending request. It admits the vector only after the
repeat finishes, including the encoded-zero count of 65536. TRAP and TRAPcc are
prohibited repeat bodies, including untaken conditions. Unsupported decoded
instructions and stack errors still use explicit library faults; this increment
does not automatically turn every such fault into an illegal/stack exception.

Directed MOVEP qualification checks ten authored X/Y/P/immediate forms in both
fast slots on reference/cached/JIT backends. Expected registers, address updates,
I/O callback PC/value and listed base costs are independent literals. A two-word
instruction in slot two refuses before I/O; a completed vector resumes its real
foreground without RTI. Captured immediate execution also restores after an
accepted peripheral write without replaying that effect. These component checks
do not calibrate interrupt-entry latency or establish derivative/device behavior.

Raw memory/program/immediate MOVEP transfers preserve the complete 24-bit bus
word with SR.SA set, including either valid scaling direction (FM3.4.1/13-134).
They do not pass through a Data-ALU register. SA Data-ALU register/accumulator
MOVEP mappings remain unsupported and refuse before the operand; non-Data-ALU
R0 reads remain 24-bit. Directed cases cover both fast slots, byte preservation,
flags/address updates, operand refusal, invalid second-slot length and a staged
post-write checkpoint. This does not qualify SA arithmetic or all register forms.

  ctest --test-dir build/strict -R '^transfer-boundaries$' --output-on-failure

  cmake --build build/strict --target dsp56300_vector_fetch_test dsp56300_vector_restriction_test
  ctest --test-dir build/strict -R '^native-vector-(fetch|restrictions)$' --output-on-failure

Vector-pair checks cover actual read order, refusal before any first-slot
effect, self-modifying P stores, fresh owners before/after first retirement,
atomic entry, prohibited MOVEM registers and invalid two-word second slots.
The fully supplied begin_instruction route retains its no-implicit-fetch
contract; a consumer choosing that route owns its captured vector inputs.

Register-MOVEP vector regression uses eight authored X0 transfers across X/Y,
high/low I/O groups and both directions in either slot. Three backends and six
publication policies cover 288 positive contexts with fresh checkpoint owners
before/after the actual operand, 288 explicit operand refusals, 1008 prohibited
source/destination cases and 48 atomic entries. It checks full registers/stack,
CCR, vector callback PC, 24-bit input masking, listed base costs and actual
foreground resumption. The identical strict test object fails on the prior core
and passes after admission is added. Other register/numerical combinations and
physical pipeline/entry timing remain separate qualification requirements.

Those vector tables identify VBA offsets 04 (illegal) and 08 (trap), and
VBA's low byte does not select the bank. The ILLEGAL entry's literal 3E vector
conflicts with these core tables; the implementation uses 04. Guest VBA writes
clear VBA[7:0] (FM5.4.4.4). Native MOVEC write/readback checks every low byte on
three backends; direct host-injected register states and wider PCU masks remain
separate qualification domains.
ILLEGAL's documented continuation is its instruction plus two. Its instruction
entry recommends abort/reinitialization; the guest's handler determines that
response. TRAP/TRAPcc continuation is modeled at the next instruction from the
generic saved-PC convention. That inference still needs hardware confirmation.
The timing table lists 5 cycles for ILLEGAL and 9 for TRAP/TRAPcc. The current
base-cost model uses those values; true/false TRAPcc pipeline timing and overlap
with injected vector costs remain uncalibrated. The documented ILLEGAL-at-LA
pipeline anomaly is not implemented. Extended stacks, SE/UF and automatic
exceptions, complete source arbitration/vector legality/numeric modes and
pipeline/event qualification remain mandatory gaps. None of these ISA rows is
complete, and this is not throughput qualification.
