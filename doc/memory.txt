Typed memory ownership and core setup

The primary setup is Core(Memory, Io*, Options). Memory is a borrowed layout,
not a storage owner or a virtual memory manager. Word is a 32-bit host value
carrying a 24-bit architectural DSP word; all extents are in DSP words.

Memory::separate(Buffers) borrows three P/X/Y views. They may overlap; aliases
are physical host-word aliases and existing executable-write invalidation applies.
Memory::unified(words) explicitly aliases all three spaces to the same backing.
Memory::partition(words, MemoryLayout{program_words,x_words,y_words}) slices one
allocation into disjoint Harvard spaces; any unused tail remains outside them.
Each logical view must be nonempty and at most 2^24 words. Partition extents are
checked before slicing, without unchecked extent sums. None of these factories
allocates, copies storage or adds dispatch to native RAM accesses.

Memory::external() leaves all storage with the supplied Io owner; a null owner
is rejected at construction. Native compilation uses the existing explicit
program/data-window grants and revision contracts. Callback refusals remain
real faults. Core(Buffers, Io*, Options) and Core(Io&, Options) remain compatible
entries into the same implementation.

MemoryArena owns the existing lazy full P/X/Y mapping and exposes memory().
A view survives an arena move if the new owner remains alive. Destroying the
owner invalidates its views. Only destroy or reassign an arena after moving it.
All borrowed backing and peripheral owners must remain stable and alive while
Core uses them. One execution owner controls state, memory and peripherals;
Memory does not provide concurrent mutation or cross-thread synchronization.

Use Core::load/write for host mutations of executable memory or P aliases so
native/decoded code is invalidated. For externally owned memory, use the owner's
program_revision and mapping contract. See io.txt and memory-windows.txt.
Core setup/cache compilation can allocate or throw; a typed view is not a
real-time audio callback guarantee. Separate host queues belong to consumers.

Focused Release qualification uses independently authored NOP/CLR/NEG programs:
partition independence, unified executable aliases and actual native invalidation,
external read/write callbacks, invalid layouts and stable moved arena ownership.
Existing alias and bounded-execution checks are rebuilt against the same SDK.
See memory-api-reference.json for the exact source and executable evidence.
No firmware input, fuzzing, whole instrument or throughput claim is involved.
