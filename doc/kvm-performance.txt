Direct and KVM translated-region measurements

This experiment executes actual DSP arithmetic translated by the ordinary x64
emitter. It compares the identical generated byte vector in a direct RX mapping
and in a KVM VM/vCPU. It does not call Core::run, execute a complete Blofeld
routine or establish whole-device capacity, sustained host load or energy.
The transparent consumer VM backend and full ISA qualification remain open.

Two own helper-free loop bodies contain one MPY or a ten-instruction arithmetic
chain covering multiplication, accumulation, addition, subtraction, absolute,
rounding, comparison and transfer. They start inside an initialized DO loop.
LC starts at iterations+1; an exact iterations*body budget ends with LC=1 and
the saved loop-start PC. Final-loop cleanup, setup and event admission are not
inside this region. The emitter retains the qualified loop guards and ordinary
fixed-point arithmetic, status flags, architectural registers and retirement.
This is neither an equivalent native algorithm nor a NOP-count benchmark.

Execution interfaces

The test-only RegionExecutor concept requires CPU/context access and exact
retirement from enter(). DirectRegion uses the production SysV entry bridge,
without generated-function pointer casts or sanitizer suppression. Its mapping
changes from RW to RX once before execution. ProtectedRegion uses guest-local
CPU/context addresses and the same emitted bytes. No host helper or memory
pointers are supplied to the helper-free guest region.

Guest::prepare installs bounded nonempty code once. Guest::enter resets the
entry GPRs/return stack and executes to the HLT boundary without copying code.
The legacy run(code) operation composes preparation and entry. Failed empty or
CPU-overlapping preparation preserves the previously installed region.
An unhandled non-HLT exit or failed entry makes the guest terminal: subsequent
entry/code preparation is rejected. In particular, an unbacked MMIO read can
never be resumed with an invented response. General exit servicing remains
future backend work.
The two KVM paths use either SET_REGS/RUN/GET_REGS, or the shared GPR image in
kvm_run with KVM_SYNC_X86_REGS. Capability discovery selects the latter when
supported; the explicit ioctl path remains available as the comparison/fallback.
Only the GPR valid/dirty bits are set. EINTR retries do not reapply entry state
after execution may have started. This is an experimental execution contract,
not a new public DSP backend or a general sandbox-security qualification.

Protocol and qualification

Build dsp56300_kvm_translation_test and dsp56300_kvm_bench with both ordinary
release/strict presets. Run through the granted group in an existing session:

  sg kvm -c 'ctest --preset release -R "^kvm-(translation-experiment|prepared-regions)$" -V'
  sg kvm -c 'ctest --preset strict -R "^kvm-(translation-experiment|prepared-regions)$" -V'
  sg kvm -c 'taskset -c 2 build/release/dsp56300_kvm_bench --bench'

Each configuration passes 9016 translation/exit/preparation-boundary assertions
and 864 prepared-region assertions. The latter cover six supported numerical
modes, both bodies, 1/7/257/65535 iterations and repeated entries on all three
runtimes, with independent raw-56 expectations for every register/loop frame,
exact progress and hidden continuation. These are directed tests, not fuzz.
Old binary fixtures and the normal CPU/emitter are unchanged.

Performance uses ordinary scaling with biased rounding, nine iteration counts
from 1 through 65536 and 16 warmups per runtime. Nine trial orders alternate
direct/ioctl/shared and shared/ioctl/direct. Each trial has 16..4096 calls,
selected by the printed instruction/replay counts. Timers and retirement checks
are included; full terminal state is checked after warmup and every trial.
Compilation, mappings/VM lifetime, code installation and CPU/context restoration
are outside the timer. No timer or syscall overhead is subtracted. Three complete
process runs are pinned to CPU2 on the i5-10400, Debian kernel 6.12.113, powersave
governor with dynamic frequency, SMT disabled, EPT/VPID enabled. Raw trials, ranges, environment and hashes
remain in ignored local evidence. Values below are medians of three run medians.

Ten-instruction body, warm execution time in microseconds:

  DSP instructions/entry    direct       KVM ioctls      KVM shared
                      10      0.0334           4.0927          3.4369
                   10240     16.1584          34.1903         33.4815
                  655360   1014.6353        1880.4939       1878.6759

The generated ten-instruction body occupies 1409 bytes at every iteration count;
the one-MPY body occupies 398. Shared GPR exchange saves about 16.0% of the
ten-instruction call versus separate register ioctls (15.7% for one MPY).
At 655360 instructions the difference between the two KVM paths is negligible.
The shared KVM/direct ratios are about 102.9, 2.07 and 1.85 for the table rows.
For the longest one-MPY loop the ratio is about 1.59. Increasing the region size
amortizes entry costs but does not remove the measured long-region gap on this
host. No cause is assigned without further guest/host profiling; it is not
evidence that every DSP program has the same ratio or that isolation is free.

Further work includes explaining/reducing the remaining gap, general RAM/move
and helper/event/I/O exits, guarded long translated regions and representative
Blofeld/FFT execution with the transparent memory/event contract. A helper-free
region's throughput cannot establish the 270 MIPS full-workload baseline, its
host-load/energy target or completion of the optimization/full-ISA objective.
